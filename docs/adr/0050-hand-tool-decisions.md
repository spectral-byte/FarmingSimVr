# Decisions behind Hand Tools in the Tool Hand

Moved out of the code under [ADR-0041](0041-code-carries-no-comments.md). Related: [ADR-0029](0029-hand-tools-follow-the-tool-hand.md), [ADR-0030](0030-spray-can-and-horse-brush-join-the-tool-hand.md), [ADR-0031](0031-the-fishing-rod-joins-the-tool-hand.md).

## Context and Decision
This record holds the non-obvious decisions behind Hand Tools: the wraps of the game's tool classes, where each tool sits and points, the chainsaw, the spray can, the horse brush and the fishing rod. They used to be comments next to the code. Each entry names the symbol or the line its comment stood at, so that a search for the symbol finds it. The wording is the comment's own: "below", "above" and "this file" mean the file in the heading, and a bare ticket number (`#164`) is a number of the old issue tracker.

### `mods/FS25_VRCompanion/src/VRCompanionHandTools.lua`

- **`SETTING_KEY_TOOL_HAND`**: Settings: the Tool Hand vrToolHand left|right: saved, default right. VRCompanion.toolHand is nil (the right hand) or a hand id; getToolHand answers it. Everything the Tool Hand does follows it: the tool's place, the trigger use, the Pointer Hand rule and the held-tool pose all read getToolHand() live, so changing it moves them on the next update (setToolHand also moves the tool at once).
- **`SETTING_KEY_CHAINSAW_REACH`**: Settings: the chainsaw's reach vrChainsawReach [\<metres> | default | game]: saved. How far past the tip of its bar the chainsaw in the Tool Hand still finds a trunk (see "The chainsaw's reach"). VRCompanion.chainsawReach is nil (the default: the mod sets no limit, the game's own reach and end-of-cut rule; `game` says the same) or a number of metres (a limited reach: `vrChainsawReach 0.15`, a hand's width, finds a trunk only where the bar is against it).
- **`VRCompanion:loadChainsawReachSetting`**: A key that is missing keeps the current value; one that is not a reach is the default (an old file with a number keeps it, one with `game` or `default` has the game's own reach).
- **`chainsawTipReach`**: How far past the tip of its bar the chainsaw finds a trunk, in metres: the setting. nil when the setting is the default, the game's own reach.
- **`FISHING_ROD_KIND`**: Supported tools The tools that go into the Tool Hand, recognised by the specialization table the game gives the tool (`spec`). A new tool is added here, with a HAND_TOOL_HANDLE_OFFSETS entry of the same kind. `useHandler` is the name of the tool's own function the game's ACTIVATE_HANDTOOL binding calls (callback(self, action, inputValue)); the Tool Hand's trigger calls it too (see "Trigger"). The lance washes while the input is held. `useHandlerClass` (optional) names the global specialization class to look the handler up on when the tool does not carry it itself: the game registers some handlers as functions of the tool (the lance's onWashAction) and leaves others on the specialization class only, called with the tool as `self` by the action event (HandToolChainsaw.onCutAction). `useHandlerSpecialization` (optional) names the specialization whose class to look the handler up on when that class has no global name (a DLC's: its scripts run in their own environment): the class is the tool's own, in tool.specializations next to its name in tool.specializationNames. `useOnce` (optional) marks a tool whose handler is called once per press and once per release, as the game's action event does for it (the chainsaw's, registered for trigger up and down), not on every update the input is held (the lance's). `toggle` (instead of a useHandler) makes the trigger a PRESS: each pull of the trigger calls toggle(tool) once. `fields` (optional) are what this module reads of a tool whose class it cannot check at map load (a DLC's): each { name, type }, a path in the tool's spec table ("fishingLine.isInitialized") or, with `onTool`, a field of the tool itself. They are checked with the handler, once per tool (see toolProblem).
- **`toggleFlashlight`**: The flashlight: a press of the trigger switches it on or off through the flashlight's own switch, HandToolFlashlight:setFlashlightIsActive (the same call the game's network event makes; no `noEventSend`, so other players see the light). The player keeps its own flag for the light (Player.isFlashlightActive, which the game restores the light from when a Hand Tool is dropped), so that follows. The game's own toggle is the action TOGGLE_LIGHTS_FPS (`F`), whose handler (PlayerInputComponent:onInputToggleFlashlight) is stripped from the readable source; the mod never calls it. Reported working in the headset on 2026-11-26 (spectral-byte/FarmingSimVr-issues#229, a summary after the session, no log kept): the trigger switches the light on and off, `F` stays in step with the trigger, and after switching to another tool and back one pull switches the light on. setFlashlightIsActive and Player.isFlashlightActive are enough.
- **`SUPPORTED_TOOLS`, `{ kind = "spraycan", label = "spray can", spec = "spec_sprayCan", useHandler ...`**: The spray can (ADR-0030). The kind is the name `vrHandToolOffset` takes. activateSpraying only sets a flag (the can's own update acts on its rising edge and clears it), so, as the lance's, it is called every update the trigger is held.
- **`SUPPORTED_TOOLS`, `{ kind = "horsebrush", label = "horse brush", spec = "spec_horseBrush", useHa...`**: The horse brush (ADR-0030). Its handler is held (spec.isCleaning = inputValue > 0) and lives on the specialization class only, like the chainsaw's cut handler; it is called every update the trigger is held, then once with 0 when it is let go or the brush leaves the hand, because the brush's cleaning flag changes only when the handler is called.
- **`SUPPORTED_TOOLS`, `{ kind = FISHING_ROD_KIND, label = "fishing rod", spec = "spec_pdlc_highlands...`**: The fishing rod (ADR-0031), from the Highlands Fishing DLC. A game without the DLC never holds one. Its ACTIVATE_HANDTOOL handler fires on press and release only (#125): held, it charges a cast, let go it throws it, and it hooks and reels the same way, so it is `useOnce` like the chainsaw's. The handler is on the DLC's specialization class, which has no global name: it is looked up among the rod's own specializations by the specialization's name (`useHandlerSpecialization`). Its fields are what the rod's state reader and its diagnostics read (#125; see "The fishing rod's state").
- **`VRCompanion.HAND_TOOL_HANDLE_OFFSETS`**: WHERE EACH TOOL SITS IN THE HAND: the pose of the tool's ROOT node in the Virtual Hand's grip frame (the frame of the holder node: origin at the centre of the tube the closed fingers form, -Y toward the fingertips, -Z from the little finger toward the thumb, +X out of a left palm and into a right one; VRCompanionVirtualHands.lua). The one place to adjust how a tool sits in the hand. The rotation maps the tool's own axes onto the hand's so that the tool points where the fingers point: the tool's +Z (the lance's nozzle runs along it) onto the grip frame's -Y, the tool's +Y (up) onto -Z (toward the thumb), which is the half turn about (0, 1, -1) below. Metres, a unit quaternion. With that rotation, putting the grip origin on the tool's own point P = (px, py, pz) (tool axes) means the root sits at (px, pz, py) in the grip frame. The handle points come from the game's own tool models (data/handTools/\*\*.i3d, in the root's axes): the chainsaw's rear handle is its `rightHandTarget` node. Tuned in the headset (vrHandToolOffset) for the right hand; only this table changes. BOTH HANDS use the same entry: a point of the tool is put on the grip origin of either hand.
- **`VRCompanion.HAND_TOOL_HANDLE_OFFSETS`, `lance`**: The lance: the hand 4 cm further back along the lance than the root (grip at tool z = -0.04).
- **`VRCompanion.HAND_TOOL_HANDLE_OFFSETS`, `flashlight`**: The flashlight lies across the fist, its lens out between the index finger and the thumb: the tool's +Z halfway between the fingertips (-Y) and the thumb (-Z) of the grip frame, a half turn about (0, 0.9239, -0.3827); 2 cm along the hand's thumb side from the root.
- **`VRCompanion.HAND_TOOL_HANDLE_OFFSETS`, `chainsaw`**: Chainsaw: the saw's bar runs along the tool's +Z, as the game turns the model (setDirection) to point its +Z where the camera looks. The hand holds the rear handle (the game's model has it at (0.056, -0.042, -0.326) of the root), turned like the flashlight, the bar between the index finger and the thumb.
- **`VRCompanion.HAND_TOOL_HANDLE_OFFSETS`, `spraycan`**: The spray can stands upright in its i3d with the nozzle along its +Z: held like the lance, the tool's +Z along the fingers and its +Y (up, the can's body) toward the thumb, the hand 5 cm up the can from the root (grip at tool y = 0.05) and 1 cm to the tool's -X side. Tuned in the headset with vrHandToolOffset spraycan (from a first guess of 10 cm up and centred).
- **`VRCompanion.HAND_TOOL_HANDLE_OFFSETS`, `horsebrush`**: The horse brush's bristles (the `fibers` shape, 4 cm below the brush node) face the tool's -Y; held with the bristles along the fingers, the tool's axes the hand's (no turn), so the hand lies on the back of the brush. The hand sits where the game's own third person hold does (the tool's `handNode` at (0, -0.009, -0.117) of the root), which puts the root at the opposite of that in the grip frame. That was the first guess from the i3d; these numbers were fitted in the headset (vrHandToolOffset horsebrush).
- **`VRCompanion.HAND_TOOL_HANDLE_OFFSETS`, `fishingrod`**: The fishing rod runs along the tool's +X from its root to its tip (see HAND_TOOL_POINTING_AXES). Held like the flashlight, through the fist with the tip out between the index finger and the thumb, the reel below. The first guess put the hand on the root itself (the DLC's i3d is packed and the probe dump, #125, names the rod's `handNode` without its position); these numbers were fitted in the headset (vrHandToolOffset fishingrod).
- **`chainsawMinimumCutDistance`**: The game's minimum cut distance for the chainsaw (HandToolChainsaw.MINIMUM_CUT_DISTANCE): the nearest a trunk can be to the targeter's ray start and still be found. The value is stripped from the readable game source, so it is read here and not written down. nil when the class or the field is missing, or the field is not a number.
- **`chainsawReachBehind`**: The chainsaw's `reachBehind` (HAND_TOOL_POINTING_AXES): the game's minimum cut distance, or nil, which leaves the ray where it is (not moved back), and the reach below off: the chainsaw then reaches and stops as in the game. ONE warning is logged the first time it cannot be read.
- **`chainsawLowerEdge`**: Where the chainsaw's ray starts on the root (HAND_TOOL_POINTING_AXES): the bar's axis, at the height of the chainsaw's own cut node (the chain's lower edge), in the root's axes. The height is the model's as the i3d has it, with the model unrotated under the tool (the mod keeps it so): the cut node's position in the model's axes, placed at the model's rest under its parent. Its live position is no use, it rides the cut guide while cutting. nil when the cut node cannot be read (none, the root the game falls back to, one that is no node or not part of the model), which leaves the ray on the bar's centre line, at the root's height.
- **`VRCompanion.HAND_TOOL_POINTING_AXES`**: WHERE EACH TOOL POINTS (the look ray): the ray the game's targeter casts starts at `node(tool)`'s origin and runs along `direction`, a unit vector in that node's own axes. One entry per tool kind, the place to adjust how a tool aims. The lance washes from its raycastNode along that node's +Z axis, the nozzle. An entry may also have a `position`, the point of the node the ray starts at (default: the node's origin); `position`, `direction` and `reachBehind` are values or functions of the tool that answer one. The flashlight's beam leaves its lens the way the game's own placement (HandToolFlashlight:updateTransform) takes it out of the tool model: from the point `lightNodeOffset` of the node the light node was below (`lightNodeParent`), along `lightNodeForward` in that node's axes. Reported working in the headset on 2026-11-26 (spectral-byte/FarmingSimVr-issues#229, a summary after the session, no log kept): the lance cleans where its jet hits from about 3 m, and the flashlight pointed at a tractor 2 m away brings up the enter prompt. The game's flashlight i3d turns the light node 180 degrees, so `lightNodeForward` is (0, 0, -1), which read at the desk as a ray toward the wrist; the headset report says the ray aims where the lens points, so the direction is left as it is.
- **`VRCompanion.HAND_TOOL_POINTING_AXES`, `chainsaw`**: Chainsaw: from the tool's root along its +Z, the bar. The root, not the model node: the game turns the model toward the camera each update and moves it along the cut while cutting, while the root stays where the hand put it. The hit point of this ray on the trunk is where the game puts the cut plane's node, so the cut height is where the bar meets the trunk. `reachBehind` is the game's minimum cut distance, read at runtime (chainsawReachBehind): the targeter finds no trunk nearer to the ray's start than that, so the ray starts that far behind the bar's base and a trunk the bar is against or in is found. When the minimum cannot be read the ray is not moved back and the reach below is not applied. `position` lowers the start to the chain's lower edge, the height of the chainsaw's own cut node (chainsawLowerEdge): a felled log is found as soon as the chain rests on it, and the cut is where the chain meets the bark. `barLength` (metres, from the root along +Z to the tip; 0.4 fits the game's models) and `tipReach` (how far past the tip a trunk is still found; a hand's width, the value to type for a limited reach: `vrChainsawReach 0.15`) describe the bar for the limited reach (see "The chainsaw's reach"); by default the chainsaw has the game's own reach and only `barLength` would count. Reported working in the headset on 2026-11-26 (spectral-byte/FarmingSimVr-issues#229, a summary after the session, no log kept): the Cut Ring shows with the bar flat against a standing trunk at its base, middle and tip, the cut starts level with the chain's lower edge, and the ring shows as soon as the chain rests on a felled log. Not recorded: the minimum cut distance `vrHandToolsDiagnostics` prints, and where the ring appears against the tip with `vrChainsawReach 0`, so `barLength` and `tipReach` are still unchecked.
- **`VRCompanion.HAND_TOOL_POINTING_AXES`, `spraycan`**: Spray can: the can's visual node (sprayCan_vis, the game's shake node, which the game moves a few centimetres while the can sprays) along its +Z, the nozzle. `reachBehind` (optional, metres): the look ray starts this far BEHIND the point the tool points from, along its axis. The game's targeter measures a tree's distance from the ray's origin and finds none nearer than HandToolSprayCan's 0.5 m, so the origin is moved back by exactly that: the can finds a trunk from right against the nozzle (0 m) to 1 m past it (the game's 1.5 m reach). A tool without the field (the lance, the flashlight) has its ray unchanged. The shake cannot move the marker: the can reads its target and hit point on the press, before the shake starts, and the shake only moves the node, never turns it. Reported working in the headset on 2026-11-26 (spectral-byte/FarmingSimVr-issues#229, a summary after the session, no log kept): the marker lands where the can points at the pull, and the can does not drift or bob in the hand standing or walking, although the game's HandToolBob moves `graphics`, the node above the can's.
- **`VRCompanion.HAND_TOOL_POINTING_AXES`, `horsebrush`**: Horse brush: the brush node (`brush`, the game's sway node: it moves a few centimetres while the brush cleans) along its -Y, toward the bristles. `reachBehind` is the game's 0.5 m minimum for animals; `touchReach` (metres) is how far past the bristles an animal still counts as touched (see "The horse brush"). The sway moves the brush node up to 5 cm along its Z every update while it cleans, square to the ray, so the ray's start jumps but not its direction. Reported working in the headset on 2026-11-26 (spectral-byte/FarmingSimVr-issues#229, a summary after the session, no log kept): the cleaning stays steady on a horse's flank and does not stutter on its edges, so the ray keeps the brush node rather than the tool's root.
- **`VRCompanion.HAND_TOOL_POINTING_AXES`, `fishingrod`**: Fishing rod: from the rod's root the way its face points, its -Y, square to the rod and toward the reel, with no `reachBehind` (ADR-0031). The DLC throws its cast along the look ray, so this is the way a real cast goes: the tip swings toward the face, and a rod held upright casts straight ahead. The handle offset fitted in the headset lays the rod's +X (root to tip) along the fist toward the thumb and its +Y onto the back of the hand. Found in the headset (#140): +Z, the game's tools' axis, is the rod's side (the cast went 90 degrees to the right); +X, the rod's length, threw an upright rod's cast into the ground.
- **`WRAP_SPECS`**: Wraps The game functions Hand Tools wrap or rely on, declared to the core's wrap helper (VRCompanionGameWraps.lua, which says what each field means), keyed by a name of the function wrapped (`fn` is its name on the class when two classes have an `onUpdate`). The wrappers (`make`) are attached by the sections that own them, which need locals defined below this table; an entry without one is CHECK-ONLY: a function the Subsystem depends on but does not wrap, which is only checked at map load (the feature gives up when it is missing or reshaped). Every function the Subsystem depends on is listed here, so that the give-up check knows all of them.
- **`WRAP_SPECS`, `getLookRay`**: SHARED: the helper's look ray wrap "lookRay", which Object Grab holds too; this Subsystem holds it while it has not given up
- **`WRAP_SPECS`, `chainsawOnUpdate`**: The chainsaw: the specialization's update (the game's event dispatch reads it off the class at every call) and its roll action's handler
- **`WRAP_SPECS`, `flashlightBeam`**: The flashlight's update, which places the light node (the instance's updateTransform is a copy made when the tool was made, which a wrap of the class would not reach)
- **`WRAP_SPECS`, `sprayCanOnDraw`**: The draw events of the tools that draw at the centre of the view (see "No screen-centre overlays")
- **`WRAP_SPECS`, `horseBrushLookup`**: The horse brush's animal lookup, which its update calls through the class (see "The horse brush's touch"), and its use handler, which the trigger calls (CHECK-ONLY: a game without it gives Hand Tools up, rather than the trigger doing nothing unseen)
- **`WRAP_SPECS`, `playerCameraGetRotation`**: CHECK-ONLY, never wrapped: the chainsaw's cut plane takes its heading from camera:getRotation, which updateChainsawFromTheTool answers differently for the length of the chainsaw's own update by shadowing it on the camera instance. The shadow depends on the camera having that function, so a game without it gives Hand Tools up.
- **`wraps`**: Giving up (ONE warning, every wrap lifted, so that the game's Hand Tools are exactly the game's) leaves Object Grab alone: it holds the look ray wrap itself. A game without a class at all has no Hand Tools to move, which is not a failure.
- **`USE_HANDLER_SHAPE`**: A TOOL WHOSE CLASS HAS NO GLOBAL NAME (the fishing rod's, a DLC's: SUPPORTED_TOOLS[].useHandlerSpecialization) cannot be checked at map load: its class is only reachable from a tool. It is checked when the local player's tool would go into the Tool Hand, once per tool: its use handler, and the fields this module reads of it (SUPPORTED_TOOLS[].fields). A tool found reshaped (its use handler missing or not the shape the trigger calls, a field missing or of another type) is left to the game for the rest of the map, with ONE warning; the other Hand Tools are unaffected. A tool found as expected is not checked again: a read of it that fails later is the reader's to answer (the rod's state is then "unknown"). A game without the DLC never holds one, so nothing is checked or warned.
- **`TOOL_FIELDS_GRACE_MS`**: How long, held, a tool's fields may be missing or of another type before the tool is found reshaped. The game attaches the real rod before it has a state (spec.state is nil until its first update while held; the headset, 2026-10-18), so a field found wrong at the attach is not yet a reshape; the tool is in the hand meanwhile and its reader answers "unknown".
- **`carryingPlayer`**: The player who carries the tool, when that is the local player: the one whose Motion Controllers these are. The game attaches the Hand Tools of the other players of a multiplayer session through the same functions, and those stay the game's (they are drawn in the avatar's hand as ever); nil for them, and when the game does not say who the local player is.
- **`toolHandFor`**: Whether the Tool Hand holds the tool now: the feature is on, Motion Controllers are on, the tool is supported and held by the local player in the first person view (the game keeps its own third person placement), and the Tool Hand's Virtual Hand is there to hold it (the hand in use, its grip pose tracked, the head placed in the world). Answers the hand, or nil and why not. Read live, never cached, by the wraps and by the update.
- **`WRAP_SPECS.attachToolToCamera.make`**: The wrap of HandTool:attachToolToCamera: a supported tool goes into the Tool Hand while it holds it, anything else (and everything while the hand does not) is the game's own.

A node is only guessed from the number: a whole number above 1 (1 is the engine's root node, and far more often a count or a direction) the engine says is an entity, whose name is not a file path (images and sounds have ids too). A plain number that happens to be a node's id is still shown with its name; in a log read by a person that is harmless.
- **`describeSpecializationClasses`**: Each specialization of the tool: its class (the game keeps it next to the specialization's name) with the global name it has, and the functions on it, where handlers kept on the class only (the chainsaw's, the horse brush's) are.
- **`edgesOf`**: The edges an action event fires on, as registerActionEvent takes them: triggerDown (the press), triggerUp (the release) and triggerAlways (every frame the input is held).
- **`describeActionEvents`**: The tool's registered action events, as the game keeps them: the action's name, the callback's name where it can be found, and the edges. The game may keep the details with the input binding's event (named by `actionEventId`): read from there too.
- **`describeNodes`, `local ok, err = pcall(function() walk(root, tostring(getName(root)), 0) end)`**: A node that cannot be read ends the walk, not the description: the lines already added stay, and so does the count of the nodes left out before the failure (the failure is a line after it).
- **`describePlacement`**: Whether the game's last placement of the tool was HandTool:attachToolToCamera (it links the tool to the camera when the player is in the first person view) or another path (attachToolToHand in the third person view, or whatever else a tool does). This is only known from the wrap of attachToolToCamera, which noted the tool when the game placed it (state.cameraPlacedTool); without the wrap (the game's function is missing or reshaped, or Hand Tools gave up) nothing was noted, and the path is said to be unknown, not another one. The game places a held tool again whenever the view changes, so a tool noted in the first person view that is now seen from the third person view has been placed by another path since (nothing is wrapped to see that).
- **`describeUnsupportedTool`**: The lines that describe the tool, without the tags, at most PROBE_MAX_LINES in all: when lines are left out, the last of those lines is the one that counts them (it takes the place of the last line kept, which is counted too). The parts that are short and tell most come first; the spec tables, which have no limit of their own, come last and are what a cut takes.
- **`MAX_NUDGE_METRES`**: Tuning: vrHandToolOffset Moves or turns a tool in the Tool Hand while the game runs, to find the numbers of HAND_TOOL_HANDLE_OFFSETS in the headset (this session only: the table in this file is what ships). The answer, and the log, carry the resulting numbers as the table has them, ready to be written down.
- **`VRCompanion:consoleCommandHandToolOffset`, `turn`**: About the hand's own axes: the turn goes in front of the tool's rotation in the grip frame.
- **`VRCompanion:releaseHandToolsFromHands`**: Called by the Virtual Hands just before they delete their nodes: the tool hangs below one, and deleting the node would delete the tool. It goes back to where the game puts it.
- **`VRCompanion:resetHandTools`**: Map unload: the tool goes back to the game's placement (the Virtual Hand it hangs below is deleted next), the wraps come off and everything seen this session is forgotten. The saved setting stays as it is. The registry removes the commands.
- **`registerSubsystem "handTools"`**: Map load: the class is wrapped again (resetHandTools lifted the wrap with the last map), then checked. Map unload: the tool goes back to the game and the wraps come off. Order. Map unload runs in reverse file order, so this one runs after Object Grab's and before Virtual Gamepad's, Wheel Grab's and the Virtual Hands': the tool hangs below a Virtual Hand, so this unload must come before the Virtual Hands delete their scene (they also call releaseHandToolsFromHands as they go). That holds as long as Hand Tools load after the Virtual Hands in modDesc.xml. Object Grab and Hand Tools wrap different classes (they share only the look ray wrap, which the wrap helper lifts when the last holder lets go), so which of the two lifts its wraps first does not matter.
- **`VRCompanion.HandTools.probeReaders`**: The probe's readers of an unknown table (the dialog probe, VRCompanionDialogProbe.lua, dumps with them): a short text for a value, the sorted keys, the function names of a table and the global name a table is kept under.
